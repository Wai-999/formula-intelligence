# Migration Risks & Rollback — Phase 0

Each risk has a **gate**: the evidence that must exist before the risky change merges. Rollback for every phase is the same baseline: work lands only through PRs from `upgrade/*` branches; `main` (which auto-deploys to GitHub Pages) changes only with owner approval; any release can be reverted with `git revert <merge>` and a re-deploy, **provided** no irreversible storage write has happened — which is why R-03's backup gate comes first.

## Rollback procedure (all phases)
1. Every phase merges as one PR → one merge commit on `main`.
2. Revert: `git revert -m 1 <merge-sha>` → push to `main` (owner-approved) → Pages redeploys.
3. Storage: until R-03's export exists, **no phase may change the shape or key of any persisted value**. After it exists, every migration writes new keys and keeps the originals for at least one release, so a reverted build still finds the old data.
4. Learner-facing recovery: Settings → Export backup before upgrading (to be built in Phase 1, first).
